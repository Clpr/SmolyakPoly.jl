# Plan: Implement `SmolyakPoly.jl`

## 0. Objective

Implement a small, portable, performance-oriented Julia module for sparse-grid
polynomial approximation of scalar-valued functions

\[
f:\mathbb{R}^D \rightarrow \mathbb{R},
\]

with the following design goals:

1. The core CPU implementation must be usable by copying a single file,
   `SmolyakPoly.jl`, into another project and calling `include(...)`.
2. CUDA and Apple Metal support must be optional sidecar extensions:
   - `SmolyakPolyCUDAExt.jl`
   - `SmolyaxPolyMetalExt.jl`
3. The core mathematical abstractions must be independent of hardware.
4. Grid construction and polynomial approximation must be independent:
   - sparse-grid accuracy is controlled by the grid;
   - polynomial accuracy is controlled by the basis;
   - interpolation is only a special case.
5. CPU, CUDA, and Metal evaluation must expose the same public semantics.
6. Performance, type stability, predictable memory layout, and code clarity have
   highest priority.
7. The implementation should target Julia 1.12.3.
8. The project must use a local Julia environment in the working directory and
   must not modify the global Julia environment.
9. All public and internal functions, structs, and macros must have standard
   Julia docstrings describing purpose, arguments, returns, and expected
   possible types.
10. Code must remain human-readable and understandable without reverse
    engineering implementation details.

The API must follow the updated usage example exactly unless this plan explicitly
states a lower-level implementation detail that does not affect the public API.

## 4. Type-stability policy

Do **not** mechanically annotate every function argument with concrete types.

Instead:

1. Every struct field must have a concrete or parametric type.
2. Avoid abstractly typed fields such as:
   - `Vector{Any}`
   - `AbstractVector` as a stored field
   - `Function` as a stored field
   - untyped dictionaries in hot paths
3. Performance-critical functions must be type-stable.
4. Public function arguments should be type-restricted only when the restriction
   expresses semantic dispatch or prevents ambiguity.
5. Generic callable objects must be accepted naturally without requiring
   `::Function` or a hypothetical `::Callable`.
6. Use Julia specialization rather than unnecessary argument annotations.
7. Add type-stability tests for core hot paths using `@inferred` where suitable.
8. Inspect representative hot functions with `@code_warntype` during
   development and eliminate avoidable type instability.

## 5. Mathematical architecture

Implement the pipeline as five orthogonal mathematical/runtime layers:

\[
\text{Domain}
\rightarrow
\text{Grid}
\rightarrow
\text{Basis}
\rightarrow
\text{FitPlan}
\rightarrow
\text{Approximation}
\rightarrow
\text{Prepared Evaluator}.
\]

Interpretation:

1. `BoxDomain`
   - where is the function defined?
2. `SmolyakGrid`
   - where should the expensive function be evaluated?
3. `ChebyshevBasisSpec`
   - in which finite-dimensional polynomial space is the function represented?
4. `FitPlan`
   - how are coefficients recovered efficiently and repeatedly?
5. `SmolyakApproximation`
   - what fitted mathematical function has been obtained?
6. prepared evaluator
   - on which hardware and at which precision is the approximation evaluated?

Hardware choice must not contaminate the mathematical definitions.

## 6. Scope restriction

Support only scalar-valued functions:

\[
f:\mathbb{R}^D \rightarrow \mathbb{R}.
\]

Do not implement native support for

\[
f:\mathbb{R}^D \rightarrow \mathbb{R}^M.
\]

Users can construct several independent approximations if they need several
outputs.

Support only bounded box domains.

Remove all Gauss-Hermite and unbounded-domain functionality.

Use Leja nodes as the sparse-grid one-dimensional node rule.

## 7. `BoxDomain`

Implement a parametric struct conceptually similar to:

```text
BoxDomain{D,T}
```

It must store:

- lower bounds;
- upper bounds;
- any precomputed affine-transform constants useful for fast conversion between
  physical coordinates and canonical coordinates.

The constructor must be non-parametric from the user perspective:

```text
domain = SmolyakPoly.BoxDomain(lb, ub)
```

Infer:

- dimension `D`;
- promoted floating-point type `T`.

Validation:

- `length(lb) == length(ub)`;
- `D >= 1`;
- every lower bound is finite;
- every upper bound is finite;
- `lb[d] < ub[d]` for every dimension.

Public API:

- `SmolyakPoly.dimension(domain)`
- `x in domain`
- `SmolyakPoly.project(domain, x)`
- `SmolyakPoly.to_canonical(domain, x)`
- `SmolyakPoly.from_canonical(domain, ξ)`
- `rand(rng, domain)`
- `rand(rng, domain, n)`
- `SmolyakPoly.sobol(domain, n)`

Semantics:

- canonical coordinates lie in `[-1, 1]^D`;
- point APIs accept vector-like inputs of length `D`;
- even for `D == 1`, a point is a one-element vector-like object;
- batch APIs return dense matrices with shape `(npoints, D)`.

Do not overload `Base.ndims` to mean state-space dimension.

## 8. Bulk point storage

Use dense matrix storage for all bulk points.

Convention:

\[
X \in \mathbb{R}^{N\times D}
\]

with:

- rows = points;
- columns = dimensions.

This convention applies to:

- `grid.nodes`;
- `rand(domain, n)`;
- `sobol(domain, n)`;
- batch approximation input;
- basis-matrix input.

Avoid `Vector{Vector{T}}`.

Do not store all nodes as `Vector{SVector}`.

Small temporary `SVector` use is acceptable only if benchmarks demonstrate a
clear benefit and it does not increase compilation burden excessively.

## 9. Multi-index representation

Create a readable internal alias or equivalent representation for fixed-
dimension multi-indices, conceptually:

```text
MultiIndex{D} = NTuple{D,Int}
```

Use a first-class sparse multi-index construction routine shared by grid and
basis logic where appropriate.

However, grid and basis must have independent index sets:

\[
\Lambda_G \neq \Lambda_P
\]

must be fully supported.

The implementation must never assume that equal grid/basis budget values imply
equal index sets.

Document the exact truncation rule mathematically.

Tests must explicitly verify anisotropic cases.

## 13. Chebyshev evaluation

Use stable Chebyshev recurrences rather than repeatedly calling expensive
generic polynomial routines.

For one coordinate:

\[
T_0(x)=1,\qquad
T_1(x)=x,\qquad
T_{k+1}(x)=2xT_k(x)-T_{k-1}(x).
\]

For multi-index \(\alpha\):

\[
T_\alpha(x)
=
\prod_{d=1}^{D}T_{\alpha_d}(x_d).
\]

Performance requirements:

- avoid allocations inside inner basis-evaluation loops;
- reuse recurrence workspace where appropriate;
- use contiguous batch-column access where useful;
- avoid materializing the full basis matrix during ordinary prediction;
- implement direct fused basis evaluation plus coefficient accumulation for
  normal approximation calls.

## 14. `FitPlan`

Implement a reusable object conceptually similar to:

```text
FitPlan{D,...}
```

Its purpose is to cache all work that depends only on:

- grid;
- basis;
- fitting method;
- ridge parameter.

Public constructor:

```text
plan = SmolyakPoly.FitPlan(
    grid,
    basis;
    ridge_lambda = 0.0,
    solver = :qr,
)
```

Required validation:

- `dimension(grid) == dimension(basis)`;
- finite nonnegative ridge parameter;
- recognized solver;
- sensible fitting-system dimensions.

Cache, where useful:

- canonicalized grid nodes;
- design matrix `Φ`;
- QR factorization for ordinary least squares;
- an appropriate stable factorization for ridge fitting;
- structural diagnostics;
- reusable CPU workspaces.

Do not solve least squares by normal equations as the default.

Prefer numerically stable QR-based methods.

If ridge is enabled, use a numerically sensible augmented least-squares
formulation or another stable method.

The plan display should report:

- number of nodes;
- number of basis terms;
- system type:
  - square;
  - overdetermined;
  - underdetermined;
- solver;
- ridge parameter;
- whether reusable factorization is cached.

## 15. Interpolation versus approximation

Do not classify a fit based on equality of grid and basis budget parameters.

Let:

\[
N_G=\text{number of nodes},
\qquad
N_P=\text{number of basis terms}.
\]

Let:

\[
\Phi_{nk}=\phi_k(x_n).
\]

Use the actual linear system.

Classification:

1. Square:
   \[
   N_G=N_P.
   \]
   If full rank, it is a valid unisolvent interpolation system.
2. Overdetermined:
   \[
   N_G>N_P.
   \]
   Use least-squares approximation.
3. Underdetermined:
   \[
   N_G<N_P.
   \]
   Reject by default unless an explicitly documented regularized strategy is
   supported.

The ordinary first implementation may simply throw a clear error for
underdetermined systems.

RMSE is an empirical fitting diagnostic.

Do not assert that RMSE is mathematically zero merely because nominal grid and
basis accuracy parameters are equal.

```text
SmolyakPoly.evaluate_nodes(
```

```text
evaluator = SmolyakPoly.prepare(
```

Its job is to hold backend-ready:

Calling:


Prepared evaluator data belong to runtime execution, not the canonical

## 30. Avoid full basis-matrix materialization during prediction

The normal evaluator must compute:

\[
\hat f(x_i)
=
\sum_{\alpha\in\Lambda_P}
c_\alpha T_\alpha(\xi(x_i))
\]

directly.

Do not implement ordinary prediction as:

1. construct `B(X)`;
2. multiply `B(X) * c`.

The explicit `basis_matrix` API may do this because the user has requested the
matrix.

The normal evaluator should fuse recurrence/basis construction and coefficient
accumulation as far as practical.

## 52. Acceptance criteria

The task is complete only when all of the following hold.

### Portability

- `SmolyakPoly.jl` alone can be copied into a Julia project and used on CPU.
- No CUDA or Metal import is required for CPU use.

### Environment

- all dependencies are local to the working-directory environment;
- `Project.toml` and `Manifest.toml` are present.

### API

- the public API follows the updated usage example;
- grid and polynomial accuracy are independent;
- the module supports scalar-valued functions only;
- bounded domains and Leja grids are supported.

### Numerical correctness

- exact polynomial-in-span tests recover coefficients to appropriate numerical
  precision;
- approximation tests behave as expected;
- interpolation is identified from the actual linear system;
- basis-matrix and direct evaluation agree numerically.

### Performance

- hot paths are type-stable;
- batch points use dense matrices;
- prediction does not materialize a basis matrix internally;
- `FitPlan` reuses fitting structure;
- prepared evaluators avoid repeated setup/device transfer.

### GPU architecture

- CUDA support is optional;
- Metal support is optional;
- GPU precision is explicit;
- unsupported precision does not silently downgrade;
- backend choice does not alter mathematical semantics.

### Testing

- CPU tests pass on Windows with Julia 1.12.3;
- CUDA tests pass where CUDA hardware is available;
- Metal tests exist but are not run on Windows.

### Documentation

- every function, struct, and macro has a proper docstring;
- important algorithms are explained in comments;
- source sections are divided with 80-column separator comments;
- a technically competent reader can understand the implementation without
  reverse engineering terse code.
